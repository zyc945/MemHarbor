## 1. 执行边界与完成标准

- T1/T2 及与它们共享的 vault 以 GitHub 私有仓库为唯一权威数据源；明确独立的 T0 vault 以本地 Git 为权威源，可以没有远端。记忆保持普通 Markdown，缓存与清单均可重建。
- 不引入数据库、LLM、Durable Objects、自动合并、OAuth、多租户或团队 ACL。
- 记忆的一次逻辑写入必须是一个 Git 提交；提交前完成校验，不得强制更新 Git ref。结果未知时先核查远端状态，不盲目重试。统一交付不要求所有源码变更挤进一个提交，也不扩大远程测试或部署授权。
- 升级保留目录及正文形态；已有合法 UUID 和 schema 3 的服务无需数据迁移。只有独立 T0 的暂空身份或更早的路径身份需要另行迁移、提交和非强制推送，不在部署时自动执行。
- 遵守 [AGENTS.md](../AGENTS.md)。只改当前阶段所需文件，保留用户已有改动，不弱化测试断言。
- 代码变更运行 `npm run typecheck`、`npm test`；传输或运行时变更加跑 `npm run test:worker`。
- 默认使用隔离本地存储。远程验收必须有明确的隔离测试目标及 `MEMORY_REMOTE_TEST=1`，不得拿生产记忆测试。
- 不打印、提交、嵌入密钥，不记录记忆正文。准确区分本地测试通过和外部验收完成。
- 每阶段完成后更新 [TODO.md](TODO.md)；记录测试、限制和未完成的外部验收。遵守文档中英文对齐约定，未翻译指南显式标注。

### 1.1 既有部署的兼容性门槛

本次源码评审基线为 `faa989e` 的 UUID/schema 3 契约；实际部署版本需在验收时确认，不据此推定所有部署都已升级。更早的路径身份、schema 1/2 仍按原迁移指南单独处理，不承诺免迁移，也不把那次迁移混入本轮升级。

- **配置不变即可运行：**旧 Worker 名称、路由、域名、R2 binding/bucket、GitHub 仓库/分支、令牌与已有 Webhook secret 全部沿用；不新增必填配置，不自动轮换密钥、改 compatibility_date/flags 或替换现有 wrangler.local.jsonc。环境类型的新字段为可选；未配置时走兼容默认值。
- **旧请求保持契约：**保留九个 MCP 工具、两种现有 MCP 传输、resources、REST 路径、权限、缺文件错误和 mutation 结果语义。旧参数请求不附加预算、不改变返回结构或隐式过滤归档主题；不因新功能未就绪而拒绝原有操作。
- **旧读取不新增依赖：**T2 的 list/search(metadata)/load/read 继续只读原 R2 对象，不访问 GitHub、不读取正文索引、不触发后台索引任务。T1 的 HEAD 刷新、内存预算和 Node 构建不进入 T2 的既有读取或部署路径。
- **发布协议不变：**不修改 `_blobs`、`_snapshots`、`_current.json` 的 schema 3 格式、键规则和 HEAD/CAS 协议。正文索引为旁路派生对象，不加入基础发布事务，也不决定 published/committed_not_published。
- **现有数据不重写：**升级不补写时间字段、不重分 UUID、不移动目录、不创建 INDEX.md、不补齐可选文件，也不因新 Markdown 解析规则拒绝原来有效的记忆。CONTEXT 以外文件的 BOM、换行、正文和原始 blob revision 继续保持。
- **内容规范不改变权限或时间语义：**不新增必填来源字段或服务端审批状态，不让普通读取刷新 updated_at 或产生 Git 写入。Skill 按任务需要通过宿主工具核验证据，不让 T2 的现有读取新增外部核验请求；旧记忆缺少来源信息仍可读写。
- **增量功能可退出：**正文索引默认关闭，可独立停用；预算模式只在显式传 max_bytes 时执行。Cron 不因代码升级自动启用，已有 Webhook 保持工作。新 Skill 遇到旧 schema 时使用原工具能力，不把功能缺失、权限或服务错误解释为可绕过服务直写 Git。
- **回滚不回滚数据：**回滚到经兼容验收的上一 UUID/schema 3 程序，只回滚应用构建和本次增加的配置，不复位 Git HEAD、不强推、不覆盖当前 R2 指针或删除旁路对象。旧程序必须可读取新程序写出的基础快照与规范文件。

一次性交付不等于一次性启用所有功能。第 6 节矩阵未通过前，不将本方案标为“可无影响升级”；默认关闭路径可以验证无新增索引 I/O，但启用后仍会产生资源成本，不能承诺绝对零性能影响。

## 2. 冻结的产品范围

| 层 | 组成 | 凭据与资源 | 读写能力 |
| --- | --- | --- | --- |
| T0-MCP | 私有 vault + Skill + GitHub 文件工具 | 仅该仓库的细粒度 PAT 或等价宿主授权 | 单文件 SHA 条件写；多文件提交要求外部保证单写者 |
| T0-Git | 私有 vault 工作副本 + Skill | 同上 | 固定读取基线、单次提交、非强制 push；分叉时停止并重新评估 |
| T1 | 本机 stdio MCP 进程 + GitHub | PAT；无额外云资源 | 复用现有九个语义工具与 MemoryService；进程内派生缓存 |
| T2 | Worker + 私有 R2 + GitHub | 新安装可用三项；旧部署保留已配置的四项 | 保留当前发布协议和已有 Webhook；新安装推荐 Cron，旧部署显式选择后才启用 |

客户端连接 T2 只配置对应权限的一个服务令牌，不需要 PAT。读写权限隔离保持现状。

当前语义工具只搜索 id/path/title/aliases/tags/description。本轮为 T1/T2 增加显式选择的正文搜索、状态/路径筛选与上下文预算；正文索引另需部署端启用，不传新参数时保留旧行为。T0 宿主自带的正文搜索不算本项目提供的等价检索能力，必须说明实际搜索范围。T1 不开放远程 HTTP 入口。

现有不可变 blob、不可变快照及 CAS 指针同样用于保护单用户并发和中断恢复；本轮不以 KV 替换 R2。`load_context_many`、S3、Deno/Bun 适配及 monorepo 拆包均为后续事项。

本轮仍保留九个 MCP 语义工具，通过现有 search/load 工具的可选参数扩展能力。时间与证据、选择性保存、巩固和一跳引用读取主要落在内容约定与 Skill；确定性的检索、预算与快照一致性落在 MemoryService。T0 共用内容约定，但不承诺服务端才具备的索引、预算或快照保障。

## 3. T0 数据与操作契约

### 3.1 规范文件和身份

- 主题位于 `<topic-path>/`；`CONTEXT.md` 必需，STATE/DECISIONS/TODO/SOURCES 四文件可选。
- front matter 仅允许 `id/path/title/status/description/aliases/tags`。沿用当前路径、NFC、状态、大小及内容校验，不新增更新时间等源字段。
- front matter 从首字符开始，不允许前导 BOM。默认单文件上限 262144 UTF-8 字节，不静默截断。
- 只有明确为独立 T0、且没有 T1/T2 读取的 vault，才可暂缺 id、使用 null 或空字符串。与现有服务共享仓库的 T0 新建必须生成合法 UUID 并遵守服务校验；不能因当前客户端没配置语义工具就假定仓库是纯 T0。已有合法 UUID 不得改写或重新分配，生成身份必须使用可靠 UUID 生成器。
- T1/T2 要求合法规范 UUID。扩展现有迁移脚本供需要迁移的 vault 显式使用，不另造工具、不在服务升级或启动时运行。现有规范 vault 的预览应为零变更。
- 精简主题可发布，但 `load_context` 所需文件缺失时会返回 NOT_FOUND；default 也需要 STATE.md。Skill 回退逐文件读取，只有确认的文件缺失可跳过，不能吞掉权限、网络或发布错误。

### 3.2 可选 INDEX.md

仅 T0 维护此派生清单。优先使用树/目录工具；无法列目录时再用清单。无清单且无法枚举时说明查找范围，请用户提供路径，不猜测完整目录。

```markdown
# Memory Index

<!-- memharbor-index:v1 -->

| path | title | status | aliases | tags |
| --- | --- | --- | --- | --- |
| 工作/基础设施/网络 | 网络基础设施 | active | ["网络配置"] | ["网络"] |
```

- 标记必须存在；固定五列，不增删列。数据行按 JavaScript 默认字符串排序规则排序 path。
- aliases/tags 使用 JSON 字符串数组，空数组为 `[]`。单元格内容先序列化，再按顺序把反斜线转义为 `\\`、竖线为 `\|`、实际 CR/LF 转为 `\r`/`\n`，保持每行一条记录；读取按反向规则解码，再解析 JSON。正文元数据不因展示而改写。
- 清单字段来自 CONTEXT.md。它不能反向覆盖源元数据，缺行不能证明主题不存在。
- 新建 vault 可创建清单；既有 vault 只有在能完整枚举并读取元数据时才生成完整清单，不能把局部结果冒充完整清单。缺少标记的既有文件不得直接覆盖。
- 已启用清单时，新建、删除、移动或修改 title/status/aliases/tags，须与清单变更同 commit。只改正文或 description 不更新清单。未启用且可用树工具的 vault 不强制建立清单。
- T1/T2 不维护 INDEX.md；切回 T0 时视其为可能陈旧，能枚举时从源文件重建，否则声明局限。

### 3.3 路由和写入选择

1. 优先选择实际可用的 MemHarbor 语义工具，检查 schema 与所需权限；工具存在不表示有写权限。
2. 无语义工具时按实际能力选择 T0-MCP 或 T0-Git。按工具功能和 schema 匹配，不硬编码宿主前缀。
3. 单文件且不涉及清单的修改，使用文件 SHA 条件写；多个文件即使只是正文，也必须单次提交。
4. T0-MCP 多文件工具若无基线条件，必须外部保证单写者；写前回读只减少竞态，不能保证安全。无法满足前提则停止该写入并建议 T0-Git/T1。
5. T0-Git 基于已读取的固定提交准备修改，只提交目标文件，非强制推送；分叉后不得通过自动合并或强推绕过重新评估。不要在脏工作副本上无条件 `git pull`。
6. T1/T2 使用对应 create/update/checkpoint/move 操作，REST delete 仅 T2 提供；不通过 checkpoint 写根目录 INDEX.md，也不以 checkpoint 代替新建、移动、删除工具。

写前预览、授权、读写分流和证据要求沿用 Skill。声明降级；结果未知时不冒称成功。单提交包含文件和清单时不会出现传输导致的“仅提交其中一部分”；发现清单遗漏属于内容错误或外部漂移，核查后修复。

已配置的语义服务发生鉴权、权限、网络、发布错误或暂时不可用时，不自动改走 T0 写同一仓库。新检索参数不被旧服务支持时，回到该服务的旧搜索/完整读取，并说明范围；不因此要求迁移部署或重新配置用户令牌。

### 3.4 移动、删除和引用

- 当前 T0-MCP 文件工具不能同提交删除旧文件并写新文件/清单，因此不提供移动或删除；工具能力变化时仍以实际 schema 和完整原子操作能力为准。
- T0-Git 可执行。预览必须区分直属规范文件与整个子树，列明子主题及附件；不得默认 `git mv`/`git rm -r` 整个目录。一次提交同步所有受影响的 path 和已启用清单。
- 替代路径必须满足同提交要求，不推荐网页先移动/删除、另交一次修复元数据的流程。
- T1/T2 move 仅作用于直属规范文件，保留子主题；T2 delete 仍只通过带 expected_commit 的 REST 接口并遵循相同直属文件边界。T1 的 stdio 不提供删除，不为此新增 HTTP 入口或破坏性 MCP 工具。
- 删除不是物理擦除。Git 历史仍保留内容；T2 旧快照及游标也可能保留已删除内容。
- T0 使用相对路径链接及正文中的关系说明，不增加 front matter 字段，不承诺解析 `memory://topics/<UUID>`。所有层均不承诺反向引用、引用完整性或级联删除；Skill 可按第 4.5 节进行有界的一跳读取。

## 4. 记忆能力的统一契约

### 4.1 研究依据、适用范围与非目标

输入为 [BiologicalandAIMemoryEvolution.md](../BiologicalandAIMemoryEvolution.md)、[deep-research-report.md](../deep-research-report.md) 与 [MEMORY-ECOSYSTEM.md](MEMORY-ECOSYSTEM.md)。采用其中关于多时间尺度、选择性保存、时间与来源、动态更新、检索控制和长期评测的工程启发，并补充使用时核验、失败经验留存、来源追踪与纠错恢复。工程调研中的部分原始出处已抽查，竞品能力与实验尚未独立复现；不将生物机制类比、项目自述、仓库元数据或厂商分数当作本项目效果与架构优越性的证明。原论文与引用完整性尚未逐项复核。

| 建议 | 本轮落实位置 | 明确的边界 |
| --- | --- | --- |
| 事实时间、来源与替代关系 | 五文件正文约定、Skill、质量案例 | 不新增源 YAML 字段，不提供任意历史时点查询 |
| 使用时证据核验 | Skill 检查当前版本、引用和适用环境 | 无法核实不等于错误；读取不自动写回或刷新时间 |
| 失败经验与来源纠错 | DECISIONS/STATE/SOURCES、授权修正与恢复案例 | 不新增必需文件，不提供自动污染清除或隔离区 |
| 从主题发现到证据定位 | T1/T2 正文派生索引、search 可选参数 | 无向量、embedding、数据库或语义推理 |
| 有预算的工作上下文 | 既有 mode + load_context 可选字节预算 | 不生成摘要，完整写入基线保持不变 |
| 经历提炼为稳定知识 | 用户授权范围内的 Skill 整理与 checkpoint | 服务端不调用 LLM，不后台摄入全部对话 |
| 过时记忆管理 | 显式筛选、正文失效标记、归档流程 | 不按年龄自动删除，不把归档当作事实失效 |
| 关联使用 | 复用既有引用，有界的一跳读取 | 不生成服务端反向索引，不递归遍历或跨主题事务 |
| 记忆质量 | 固定离线案例、检索评测、独立 Agent 验收 | 服务测试不调用模型；Agent 表现不能由单元测试代替 |

Git 是数据权威源，不是事实真实性证明；Git → R2 发布不执行知识提炼，checkpoint 的原子性不解决语义矛盾。模型参数学习、Titans 类神经记忆、自动反思循环、知识图谱数据库、在线 GC 和物理擦除均不纳入本轮。

服务端强制审批属于后续可选权限模型，不把 pending/propose 加入本轮默认写入路径。真正的审批需要独立的批准权限、绑定具体差异和基线版本、拒绝过期批准，并覆盖普通写入及 T0/T1 的直连 Git 路径；Agent 若仍持有可绕过审批的写令牌或 PAT，单加 pending 状态并不能形成强制约束。现有显式保存授权继续有效，不因新流程再次要求同一批准。

### 4.2 时间、证据与巩固

- 沿用五文件，不新增必需的 EPISODES.md、SKILLS.md 或事实数据库。CONTEXT 保存稳定背景与适用条件，STATE 保存当前状态和必要的近期结果，DECISIONS 保存采纳理由及替代关系，SOURCES 保存可定位证据，TODO 保存后续验证与行动。
- 对会变化或影响重要判断的结论，按需在正文记录：结论与适用对象/环境、生效与失效时间、记录或验证时间、来源、证据状态，以及替代了哪项结论。并非每条记忆都强制填写完整模板；未知日期省略或明确未知，不从提交时间推算。
- 区分已验证、用户陈述、待验证、存在争议、已被替代；这些是正文表达，不新增 topic.status 枚举，也不编造数值置信度。主题 completed/archived 与其中某条事实失效不是同一含义。
- updated_at 表示主题内容或路径变化的版本时间依据，git_commit 和 revision 标识版本；它们不代表事实生效时间、最近使用时间、最新核实时间或可信度。相同内容更新仍为 noop，不通过重写或 touch 提交刷新时间。记忆 URI 指向当前内容；引用特定历史结论时保留必要原文、来源定位与已知 commit，不声称 URI 固定了历史版本。
- 重要结论在正文关联稳定的主题内来源编号或锚点，并在 SOURCES 中记录实际链接、文件与已知版本、用户陈述等定位信息；区分直接观察、他人陈述和推断。编号在该主题内保持可追踪，不创建全局 ID 系统；来源未知则明确未知，不要求为旧记忆批量补齐。来源描述与自填 author 不能证明真实写入者身份。
- 使用影响当前决策的记忆前，按需核对引用位置、当前版本与适用环境，区分仍成立、已过时和暂时无法核实。引用失效不自动证明结论错误，网络/权限失败不等于不存在；无法核实则说明限制。证据矛盾时提出修正，只有授权范围包含保存时才写回；实际核验结果与时间按需记入正文，不因一次读取或核验成功自动更新。
- 新旧信息不同，先判断时间、对象和环境是否一致，再判断是更新还是矛盾。新的写入时间不能自动推翻旧证据。版本冲突继续走原并发流程；无法消解的语义矛盾保留双方依据，标为待确认。
- 整理时先保存可复用结果与证据，再按明确确认或充分证据提炼稳定结论；一次环境特定的成功不能直接推广成通用规则。可复用操作应保留前提、步骤、验证方式和失败条件。
- 对有复用价值的失败或被否决方案，沿用 DECISIONS/STATE/SOURCES 保存尝试、环境与前提、结果证据、失败或否决理由、值得重试的条件。重复尝试前先查相关记录；一次失败不是永久禁令，条件变化时允许重新判断，不增加服务端执行阻断门。
- 长过程可压缩，但保留影响判断的例外、限制和来源；只整理本次授权范围，不因读取触发更新，不自动全库重写。短期记录与稳定结论在同一主题内变更时，用一次 checkpoint 提交受影响文件；T0 遵守第 3 节单提交前提。

来源纠错是显式授权的维护任务：固定检查范围，按来源编号及原始定位查找受影响结论，人工复核后在当前基线上提交修正，保留后来有效的修改；依次处理各主题，不承诺跨主题事务。随后按现有协议发布，并仅在正文索引已启用时重建对应派生索引。默认元数据搜索不能保证找到正文中的来源，必要时在授权范围逐文件检查并报告未覆盖范围；不提供自动反向引用或完整污染清除保证。禁止通过复位 Git 历史、强推或恢复旧 R2 指针清除错误。归档不是隔离，默认搜索、直接读取和历史仍可能暴露相关内容；删除也不是物理擦除。

示例仅说明时间差异：某配置 9 月 22 日生效、9 月 24 日才录入，应分别记录这两个时间；9 月 24 日的 Git 提交不能证明配置当天才生效。服务只保存和检索这些文字，不自动判断事实有效区间。

### 4.3 搜索、证据片段与派生索引

先完善现有 list(path_prefix) → resolve(path) → read/load 与 search 的工具说明和迭代查找示例，区分主题导航与正文证据定位，不新增 grep/open 工具或改变九工具契约。文件工具的外部实验不证明索引无价值；按第 4.6 节分别评估导航流程与正文检索，保留本节显式启用边界。

**输入与兼容：**扩展 search_memories，保留 query/limit/cursor，增加显式 scope（metadata/content/all）、status、path_prefix、include_archived（默认 true）。scope 缺省走完整旧分支，只有显式 scope 才启用新搜索选项；新 Skill 即使只请求状态筛选，也发送 scope=metadata。特别是旧 REST 的 `q+status/path_prefix` 原来忽略筛选，本轮在未传 scope 时继续忽略，不让原请求悄然改变结果。未传 scope 时也不对过去忽略的字段新增校验。

增强分支中，status 沿用单一既有状态；include_archived=false 仅排除 archived，不排除 completed，与 status=archived 同用时报 INVALID_CONTENT。REST 同名参数中 include_archived 仅接受字符串 true/false 并显式转为布尔值；共享服务统一校验和筛选，拒绝非法枚举及非布尔值，不使用字符串真值转换。不要仅靠 schema 给 scope 填默认值，否则会丢失“缺省还是显式”的兼容判断。

- 原查询及显式 scope=metadata 且无实际新增筛选的等价查询，继续使用旧条件指纹 `JSON.stringify(['search', query])`；list 保留 `JSON.stringify(['list', status ?? null, prefix ?? null])`。保留原查询字节参与指纹，不因分词/NFC 归一化改变它。旧 filter/filter_hash 游标继续接受，新程序为旧查询发出的游标也应能由回滚后的旧程序消费。
- 只有实际使用新增筛选或正文范围的查询使用带版本的条件指纹，包含 query、scope、状态、路径、归档选项及检索算法版本。筛选先于排名和分页，后续页固定原快照及算法，不得切换索引版本；回滚后的旧程序不支持增强游标，应明确让客户端重开旧查询，不承诺增强游标向后可用。
- content 搜索五个规范文件的正文，不搜索 CONTEXT 的 YAML；缺失的可选文件不参与索引。先按 Markdown 标题识别章节，再按段落/完整列表项/完整代码块形成可定位块；代码围栏内的井号不是标题。保留前言、重复标题的序号、行号和原文，不把提炼后的文字当作证据。
- 索引匹配使用 NFC 与大小写归一化。初版采用原文连续短语优先、全部查询项匹配其次；英文按词匹配，中文等连续 CJK 文本使用码点二元组，单字查询保留单字匹配。规则在 Node 与 Worker 下保持一致，不依赖运行环境的分词差异。
- all 先保留元数据命中的既有排序，再补充正文命中的其他主题；正文命中按匹配等级、命中查询项数降序，最终以 UUID 稳定排序。同一主题只占一个结果，正文片段附到该主题；这是可测的初始规则，不宣称语义相关性或置信度。
- 保留 topics/total/next_cursor/git_commit，total 继续表示主题数。仅显式 scope 的成功响应额外回传 search_scope，客户端据此确认增强分支实际生效；没有回传时不能把旧服务忽略参数后的结果当作完成了正文搜索或状态筛选。content/all 的主题可带 matches，包含 file、heading_path、block_id、start_line/end_line、excerpt、revision。block_id 仅在该文件 revision 内有效，不构成新的永久身份；片段、版本和主题必须来自同一快照。
- 每个主题最多返回 3 个片段，每片段最多 1024 UTF-8 字节，超出以 truncated 明示并给出完整文件读取入口；片段截取不切坏 Unicode 字符。片段只是定位线索，不能作为完整事实或写入基线。公共索引端点不得包含这些正文片段。
- 完整文件入口仍读取当前发布版本，不是历史版本接口。搜索后再次读取若 revision 已变化，应重新核对或检索，并区分两次证据的版本，不能把新正文冒充原片段对应的内容。

**启用与旁路派生：**新增可选非 secret 配置 MEMORY_CONTENT_SEARCH，未设置或 false 时关闭，只有 true 启用；T1/T2 相同。关闭时不构建、预热、读取正文索引，也不因普通请求安排索引任务；显式 content/all 请求只报告功能未启用。上下文预算和元数据筛选不依赖此索引开关。

- 保持基础清单和指针原样，不再添加 search_index 字段。当前索引放在独立 `_search/v2/<git_commit>.json`，由已固定快照的 commit 确定；对象包含格式/算法版本、commit 和规范文件 UUID/path/revision 清单，使用前必须与固定快照核对。v2 的 integrity 保存块数量及覆盖版本、commit、来源清单和块数据的 SHA-256 摘要；另校验块 ID、来源顺序和行号连续性。版本与源内容确定输出；同一版本不静默换排序算法或覆盖有效索引。算法变化使用新命名空间并保留旧对象。
- 2026-09-29 的围栏解析与完整性修复使用 v2，不改写或删除 v1 对象。已开启正文检索的 T2 升级后须通过维护入口、后续发布或已配置的 Cron 补建 v2；T1 启动后排队构建。未就绪时正文查询明确报错。v1 正文游标返回 INVALID_CONTENT 并要求重新分页；普通查询及显式 metadata 筛选的游标指纹保持不变。
- 索引只从一份已成功发布的快照及其原始 blob 构建，完成后才一次性发布完整索引对象。基础发布不等索引，索引失败不回滚基础指针、不使已发布写入变成 committed_not_published，也不把新旧内容拼在一起。旧程序忽略 `_search/` 即可继续工作。
- Worker 的可选构建由运行时入口通过 ctx.waitUntil 调用服务方法安排在基础发布之后，捕获并单独记录索引失败；不要把裸 Promise 或可抛错的构建回调放进基础提交/发布的成功判定。显式启用 Cron 时可补建当前快照缺失的索引；未启用 Cron 的部署通过后续发布或显式维护构建重试，不自动安装 Cron。
- 提供独立的 `POST /api/v1/admin/search-index`（WRITE 权限、请求体 `{}`），仅在正文索引已启用时为调用开始固定的已发布快照构建索引；直接调用 MemoryService 方法，只写 `_search/`。完成响应为 status=search_indexed、git_commit、index_version，不表示它仍是最新 HEAD，不复用基础 published 标志。旧 reconcile 请求/响应不变；T1 由本地启动后的同一服务方法构建，不新增 MCP 工具或 HTTP 入口。普通 read/search 不触发构建，后台任务受运行时限制，不能假设 ctx.waitUntil 是可靠队列。
- content/all 固定读取快照及其对应索引；缺失、损坏、版本/来源不匹配时报 PUBLISH_ERROR，并在 details 中标明 component=search_index 和原因，不返回假空结果或用旧 commit 索引冒充当前。该错误只影响显式正文查询，原元数据查询、完整读取和写入仍可用。空库仍返回正常空结果。
- MCP schema 中存在 scope 不表示正文索引已启用或就绪。Skill 探测到旧 schema 时使用旧请求；索引不可用时，可明确说明后单独执行元数据查询，不冒称已搜正文，不把可选索引错误当成整个服务发布失败。
- T1 使用相同格式和算法；基础快照先就绪，正文索引后台可选构建。为可选索引设置独立的字节/工作量额度并计入总峰值；额度不足时保留基础服务，正文查询报告不可用，不淘汰当前基础快照或让普通启动/刷新失败。
- T2 派生索引可经 Git → 基础快照 → 索引完整重建；不增加线上 GC，不删除旧快照、blob 或仍可能被使用的索引。不把查询改成逐文件读取 GitHub；T1 的 HEAD 检查仍只属于 T1。
- 索引构建前限制输入/输出字节、块数量及工作量，分段让出执行并处理取消，不把正文解析错误变为规范数据校验错误。启用前测量现有规模和增长规模的内存、CPU、I/O；索引构建和搜索会增加成本，不承诺启用后零影响或无限容量。

### 4.4 上下文预算与写入基线

- 扩展 load_context，保留 topic/mode，增加可选正整数 max_bytes；REST 对应读取接口同步支持。上限不超过所选 mode 文件数量乘以服务的单文件大小上限。不传时，原来的 files/revisions、缺文件错误和完整内容行为不变。
- 显式传预算进入只读节选模式，复用章节/块解析。按 MODES 的文件次序轮流选取各文件的下一个完整块；放不下的块标记省略，继续检查其他块，保持输出在每个文件内的原始顺序。不拆开列表项或代码块，不生成摘要，不声称已自动识别所有重要约束。
- 预算计算返回标题路径文字与原文节选的 UTF-8 字节之和，不含 JSON、MCP 封装或元数据；不得称其为模型 token 预算。没有完整块能放入时可以返回空节选，但必须说明省略及后续读取方法。
- 预算响应使用独立的 sections 数组和 coverage，不返回可被误作完整替换文本的 files/revisions。sections 包含 file、heading_path、block_id、行号、content 和源 revision；coverage 包含 max_bytes、returned_bytes、partial、各文件 omitted_blocks 数量和完整文件读取入口，不重复省略正文或输出无界的省略清单。仍返回 topic/path/git_commit，所有节选固定同一快照。
- mode=full 与 max_bytes 同传时报 INVALID_CONTENT，避免 full 名不副实。写入前仍须 load_context(full) 或按既有精简主题规则取得同一提交的完整文件；不得拿预算响应、搜索片段或摘要拼装完整替换内容。
- 未提供预算的 MCP resource 保持当前完整读取语义。没有新增参数的旧客户端继续可用；Skill 先检查实际 schema，不向旧服务发送尚不支持的参数，并核对返回确为 sections/coverage。旧服务或混合版本部署忽略 max_bytes 而返回 files 时，不宣称预算已执行。

### 4.5 生命周期与关联读取

- 当前任务检索时，Skill 可显式选择 include_archived=false，必要时再查历史；追溯旧决策时保留归档结果并说明状态。默认服务搜索不改变历史兼容行为；不根据更新时间或访问次数自动删除、降权或归档。
- 某事实被替代时，更新当前状态并保留必要依据；整个主题归档仍需有上下文依据和授权。归档、删除当前主题和物理擦除继续采用不同表述。
- 复用 memory-links 的已验证引用，仅按当前问题展开直接相关的一跳，默认最多 3 个目标；按 UUID（T0 为规范路径）去重，不继续追踪目标的引用。超出时说明尚未读取范围，不承诺完整关联发现。
- 不执行记忆中夹带的指令，不将目标的当前内容当作固定历史证据。不同主题的独立读取可能处于不同 commit，应保留各自来源；不声称跨主题快照原子性，也不新增 load_context_many。
- 失效目标、网络/权限失败与确实不存在继续区分处理；不自动修复、删除引用、写入反向引用或级联修改关联主题。

### 4.6 质量基线与验收方式

在改动检索前冻结离线样例、预期答案/证据和原有元数据基线，至少 30 个案例，覆盖事实更新与时间差异、相似环境干扰、正文独有关键词、多来源组合、未知/矛盾、归档与无关内容增长，并纳入引用过时/失效/不可达、失败方案重试条件和错误来源纠正。使用合成数据和隔离存储；不得复制生产记忆进入测试或报告。已有检索单元测试继续保留，这组案例补齐任务层基线；自建样例不等同于完成 LoCoMo/LongMemEval 官方评测，后者需要另行准备数据、适配与回答评估流程。

- **服务层自动评测：**检索 Recall@5、来源定位正确性、默认行为回归、筛选正确性、快照一致性、正文预算和负例查询的真实空结果。Recall@5 只统计有相关主题的查询，空结果负例单独报告。精确 UUID/path 查询及一致性、权限、预算约束必须全部通过；新增正文专属案例必须召回对应主题及证据，既有元数据排序案例不得退化。
- **成本记录：**同一固定数据集记录响应正文字节、索引体积、构建/检索耗时、存储调用次数，以及 T1 发布峰值。使用固定的多个数据规模观察增长；报告运行环境、样本数和测量方法，时延不作为跨机器的硬编码 CI 门槛。
- **Agent/Skill 独立验收：**按同一案例核对是否使用过时事实、混淆环境、编造来源或将未知说成已知，是否保留适用条件，以及巩固后能否支持继续任务。记录客户端/模型版本、输入范围、预期和实际结果；单次人工验收不等于通用模型基准。
- **任务对照：**固定模型版本、数据、上下文和工具调用预算，比较原有工具/说明、改进说明与导航但关闭正文索引、同一改进流程下显式正文检索三种条件；保存各条件的 Skill/工具说明版本。分别报告任务成功率、过时事实误用、合理拒答、调用次数和实际可取得的 token 消耗；无 token 计量时单列字节，不混为一谈。普通服务测试仍不调用模型，不引用跨实验厂商分数作为提升依据。
- **来源纠错演练：**合成案例包含同一错误来源影响多个结论、独立有效来源与后续有效修改、缺失来源信息及未检查区域；验证授权范围、正向修正提交、原有有效修改保留、基础发布与已启用索引更新，并报告覆盖范围。另验只读核验无写入、noop 不刷新 updated_at、归档仍可读取及缺少新正文约定的旧记忆正常使用；不将演练宣称为自动隔离或物理擦除能力。
- 普通 npm test 和 CI 不调用模型，不把服务返回了正确片段等同于 Agent 回答正确。新增可重复的离线评测命令及脱敏报告格式；外部客户端/模型尚未验证时保留待验收项。

| 风险 | 对旧部署的潜在影响 | 修订 |
| --- | --- | --- |

### 6.2 必须通过的兼容矩阵

用固定的合成 vault 和实际上一版本程序生成基线，不能只用新版 helper 人工构造“旧数据”。旧客户端既包括原参数请求和结果消费者，也包括上一版 Skill；新客户端必须做能力探测与响应核对。所有场景先在隔离本地环境验证，需要远程证据的部分另用显式测试目标。

| 场景 | 验收要求 |
| --- | --- |
| 旧四-secret 配置 + 新 Worker，未填任何新项 | 基础 REST、两种 MCP、resources、Webhook ping/push/签名拒绝与原行为一致；不新增 Cron/索引 I/O |
| 旧客户端 + 新 Worker | 原搜索排序、返回字段、default/full 内容及错误、写入冲突/幂等/发布失败语义不变；q+status/path_prefix 仍按旧分支处理 |
| 旧游标 → 新 Worker；新默认游标 → 旧 Worker | list/search 分页保持原快照且可继续，包含原 filter 和 filter_hash 两种旧格式 |
| 旧基础快照/规范文件 → 新 Worker | 不需要先 reconcile 或运行迁移即可读；缺可选文件、中文路径、非 CONTEXT BOM 与原字节保持兼容 |
| 新 Worker 发布/写入后 → 回滚旧 Worker | 旧程序直接使用当前 Git 和 R2 数据继续读写；不恢复旧 Git 提交、不重写指针；旁路对象可以保留 |
| 新客户端/Skill + 旧服务 | schema 无增强能力时用旧参数；混合版本响应无 search_scope/coverage 时不冒称增强能力生效，不自动改走 T0 写入 |
| 正文开关关闭；开启但索引未就绪/损坏/超预算/取消 | 只对显式正文查询报告限制；默认读写、健康检查和发布结果不受索引失败影响 |
| Cron 未新增；显式增加；保留已有触发器 | 旧 Webhook 不变；启用后与写入并发仍安全；索引失败与基础同步失败可区分 |
| T0/T1/T2 共用规范 vault | T0 不生成空 UUID；已有身份、子主题和附件保持；旧服务可发布新增内容 |
| 基础读取在 GitHub 故障时 | T2 的现有已发布读取仍可用，不因共用 T1 刷新逻辑访问 GitHub；索引关闭时存储调用与原基线一致 |
| 新 Skill + 无来源标记的旧记忆；同内容重写 | 旧记忆正常读取与更新；来源不足如实说明，不自动补写；同内容仍 noop 且 updated_at 不变 |
| Skill 核验引用有效/过时/不可达 | 只读任务不产生 mutation，不自动改用 Git 写入；保存已有授权时不增加重复审批；服务默认读取无新增核验 I/O |

所有语义断言为发布门槛；构建体积、CPU/内存、耗时另记录同环境前后对比。性能结果超出预先记录的容量范围时保持新功能关闭，不能以“测试通过”替代资源评估。

### 6.3 升级与回滚顺序（实施时执行）

1. 确认实际旧版本属于已验收的 UUID/schema 3 基线；保留旧构建和部署配置，记录当前数据 commit、基础快照指针及已有触发器。只记录标识，不导出秘密或记忆正文；不暂停正常服务、不自动迁移数据。
2. 先在隔离环境运行上述矩阵与升级/回滚演练。随后如获部署授权，仅升级应用代码，沿用实际旧配置，正文开关保持缺省/false，Cron 保持原状，不用示例配置覆盖部署配置。
3. 验证旧客户端读取、权限与现有同步；新服务应能直接读取原快照，不把先执行全库 reconcile 当成基本读取的前提。不要为验证升级在生产创建测试主题，真实写入验收仍使用隔离目标。
4. 基础升级验证完成后，按需要分别启用正文索引或 Cron。正文开启后通过独立维护入口构建、确认指定 commit 已就绪，再让客户端请求 content/all；允许新发布与旁路索引之间存在明确的就绪延迟。
5. 发生回归，先停用本次新增能力；需要回滚程序时保留最新 Git/R2 数据，仅恢复已记录的应用和本次改变的配置。回滚无 scheduled 处理器的旧程序前，应先撤回本轮新增的 Cron，保留原有触发器并确认变更状态。恢复原 Webhook，禁止通过 Git reset/强推/恢复旧指针丢弃期间正常写入。
6. 新功能关闭或回滚后，增强查询/预算能力不再保证，客户端重新探测并使用旧请求；原查询的游标应继续可用，增强游标则重新开始查询。将实际验证版本、范围和未验收项记录到 VERIFICATION/TODO。
